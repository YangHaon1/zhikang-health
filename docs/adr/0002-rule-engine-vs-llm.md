# ADR-0002：规则引擎与 LLM 解耦——安全结论只能来自确定性代码

- 状态：已采纳
- 日期：2026-09-25
- 相关代码：`server/shared/health-engine.ts`、`server/src/services/health-agent.ts`、
  `health-plan-agent.ts`、`health-review-agent.ts`、`server-ml/explain.py`

## 背景

系统里有两类"结论"：

- **安全相关结论**：风险等级、急症分流、就医提醒、指标分级；
- **表达相关结论**：画像文案、改善建议、计划措辞、复评说明。

早期实现里两者边界模糊，出现过两类问题：LLM 输出被直接当成等级；
以及 LLM 不可用时整条链路没有兜底、也没有痕迹。

## 决策

1. **安全结论 100% 由确定性代码产出**：`analyzeHealth`（规则引擎）与 LightGBM 分级。
   急症分流（`checkEmergency`）走**固定文案**，绝不交给大模型自由生成。
2. **LLM 只做表达层**，且每次调用都必须能回答「这次到底走没走 LLM」：
   接口返回 `source: "ai" | "rule"`，编排链路返回 `steps[].source / degraded`。
3. **降级必须留痕**：不允许静默 `catch`。所有降级路径写 `console.warn`，
   并注明为什么必须留痕（否则现场无法区分「AI 没输出」与「输出解析失败」）。

## 理由

- **安全底线**：「我不想活了」这类输入如果先经过大模型"润色"，可能被弱化成普通建议；
  必须由关键词分支直达心理援助热线 12356，且处置步骤是写死的。
- **可验证**：评委问「你怎么证明这是真 AI 而不是写的假文案」，
  答案是让接口自己暴露 `source`，而不是靠口头保证。
- **可降级**：断网/无 key 时系统仍能完整演示，只是文案退化为规则版本。

## 被否方案

- **LLM 直接生成急症处置**：不可接受，医疗安全文案不允许生成式改写。
- **降级时静默返回规则结果**：曾实际存在（4 处空 `catch`），已全部改为留痕。

## 影响

- 前端必须展示 `source`，不能把规则文案包装成"AI 生成"（本仓库曾修过 3 处这类展示）。
- 断网时演示链路仍完整，但画像/复评耗时从 ~1.7s 降到近 0ms —— 这本身就是降级信号。
